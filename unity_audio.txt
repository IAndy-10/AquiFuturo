⏺ Good question — Transform is not a method. It's a built-in class (component) 
  in Unity, not specific to this project.

  ---
  What is Transform?

  In Unity, every single GameObject in a scene automatically has a Transform
  component. You cannot remove it. It stores three things about the object's
  location in 3D space:

  ┌──────────┬───────────────────────────────────────────────────────────────┐
  │ Property │                         What it holds                         │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ position │ Where the object is in world space (X, Y, Z)                  │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ rotation │ Which way it's facing (as a Quaternion)                       │
  ├──────────┼───────────────────────────────────────────────────────────────┤
  │ forward  │ A convenience vector — the direction the object is "looking   │
  │          │ at"                                                           │
  └──────────┴───────────────────────────────────────────────────────────────┘

  So when the docs say:

  private Transform _treeBase;

  This is a reference to the Transform component of the tree cylinder that was
  placed in AR. It's not the tree's mesh or visual — just its positional data in
   3D space.

  ---
  How it's used here

  In PoseAnalyzer, once the user places the tree, TreePlacement calls:

  public void SetTreeBase(Transform treeBase)

  Now PoseAnalyzer knows where the tree is in the world. Then, every frame, it
  can compute things like:

  // Vector from camera to tree, in world space
  Vector3 toTree = _treeBase.position - cameraPosition;

  Without Transform, there's no way to ask "where is the tree right now?" The
  Transform is Unity's answer to that question — it's the object's live
  coordinate in the scene.

  ---
  Why Transform and not just a Vector3 position?

  Because Transform is a live reference — if the tree moves (e.g. during the
  Adjusting phase), _treeBase.position always returns its current position. A
  Vector3 would be a snapshot that goes stale.

⏺ Why _treeBase?

  The name is descriptive of what part of the tree it references — not just "the
   tree", but specifically the base (ground level, root collar). The tree
  cylinder's pivot point is at its base, so _treeBase.position gives you the
  point on the ground where the trunk meets the earth. That matters because:

  - You want horizontal distance/angle relative to where you're standing near
  the tree
  - If you used the centre of the trunk (mid-height), crouching would change the
   angle calculation
  - The base is the stable anchor point regardless of tree height

  The _ prefix is the project's naming convention for private fields (from
  csharp-unity.md rules).

  ---
  Azimuth — step by step

  azimuth = Vector3.SignedAngle(camFwdXZ.normalized, toTreeXZ.normalized,
  Vector3.up);

  There are three sub-steps hidden in that one line.

  ---
  Step 1 — Flatten both vectors onto the XZ plane

  camFwdXZ = new Vector3(camForward.x, 0, camForward.z)
  toTreeXZ  = new Vector3(toTree.x,    0, toTree.z)

  Why? Because you only care about horizontal direction. If you tilt the phone
  up to look at the canopy, the tree doesn't suddenly move to your left — the
  pan shouldn't change. Zeroing out the Y component drops both vectors flat onto
   the ground plane.

  World view from above (Y axis pointing at you):

              N (Z+)
              |
      ← W --- * --- E (X+)
              |
              S

  ---
  Step 2 — Vector3.SignedAngle(from, to, axis)

  This is a Unity built-in that answers: "how many degrees do I need to rotate 
  from to reach to, rotating around axis?"

  - from = where the camera is pointing (flattened)
  - to = direction toward the tree (flattened)
  - axis = Vector3.up — meaning rotation is measured around the vertical Y axis
  (clockwise/counterclockwise on the ground plane)

  The "Signed" part means:
  - Positive = tree is to the right
  - Negative = tree is to the left
  - 0° = camera is aimed directly at the tree

  Camera pointing North (Z+):

    Tree at East  →  azimuth = +90°
    Tree at North →  azimuth =   0°
    Tree at West  →  azimuth = -90°
    Tree behind   →  azimuth = ±180°

  ---
  Step 3 — .normalized

  Normalizing a vector means scaling it to length 1 while keeping its direction.
   SignedAngle only cares about direction, not distance — normalizing ensures
  the magnitude of toTreeXZ (how far the tree is) doesn't accidentally affect
  the angle calculation.

  ---
  What the azimuth feeds into

  The raw angle (in degrees) gets smoothed, then converted to radians in
  TrackMixer:

  float panBase = Mathf.Sin(azimuthRad);

  Sin maps the angle to [-1, 1] — the exact range for stereo pan. At 0° (facing
  the tree) pan = 0 (centre). At 90° (tree to your right) pan = +1 (hard right).

⏺ Two separate reasons, both important

  ---
  Reason 1 — Preserve damping state across frames

  Mathf.SmoothDamp is not a one-shot calculation. It's a stateful spring — it
  needs to remember how fast the value was moving last frame in order to apply
  the correct deceleration this frame.

  Its signature:

  Mathf.SmoothDamp(float current, float target, ref float currentVelocity, float
   smoothTime)

  The ref float currentVelocity parameter is read AND written every call.
  SmoothDamp uses it to track momentum.

  If you used a local variable:

  void Update()
  {
      float vel = 0f;  // ← born fresh every frame, always 0
      _azimuth = Mathf.SmoothDamp(_azimuth, rawAzimuth, ref vel, 0.2f);
  }

  Every frame vel starts at zero. SmoothDamp sees "velocity = 0" and thinks the
  value just started moving. The result is no smoothing — the value just snaps
  to target instantly. The damping is broken.

  With a private field:

  private float _azimuthVel;  // ← lives between frames, retains momentum

  void Update()
  {
      _azimuth = Mathf.SmoothDamp(_azimuth, rawAzimuth, ref _azimuthVel, 0.2f);
  }

  Frame 1: _azimuthVel starts at 0, SmoothDamp accelerates toward target, writes
   back e.g. 0.3
  Frame 2: _azimuthVel is still 0.3, SmoothDamp uses that momentum to continue
  the curve smoothly
  Frame 3: decelerating as it approaches target...

  The damping curve only works because the velocity persists.

  ---
  Reason 2 — Avoid heap allocations

  This one is subtler. In C#, float is a value type — it lives on the stack, not
   the heap. So storing four floats as fields doesn't allocate heap memory.

  The rule exists to guard against a common mistake: wrapping state in an object
   or closure that would allocate:

  // Bad — creates a new object every frame
  var state = new SmoothState { vel = 0f };

  Or accidentally using a lambda/delegate that captures a local:

  // Bad — closure captures local, allocates on heap
  float vel = 0f;
  Action smooth = () => Mathf.SmoothDamp(..., ref vel, ...);

  Heap allocations in Update() are a problem in Unity because the garbage 
  collector eventually runs to free that memory — and when it does, it causes a
  frame stutter. On a phone running AR (already CPU/GPU heavy), a GC spike drops
   frames visibly.

  ---
  The combined rule

  ┌─────────────────────────┬────────────────┬───────────────┐
  │                         │ Local variable │ Private field │
  ├─────────────────────────┼────────────────┼───────────────┤
  │ Lives between frames    │ No             │ Yes           │
  ├─────────────────────────┼────────────────┼───────────────┤
  │ Damping works correctly │ No             │ Yes           │
  ├─────────────────────────┼────────────────┼───────────────┤
  │ Heap allocation risk    │ Possibly       │ No            │
  ├─────────────────────────┼────────────────┼───────────────┤
  │ Correct for Update()    │ Never          │ Always        │
  └─────────────────────────┴────────────────┴───────────────┘

  This is why the four velocity refs exist as plain private floats on
  PoseAnalyzer:

  private float _azimuthVel;
  private float _alignmentVel;
  private float _tiltVel;
  private float _distanceVel;

  One per axis. Small, stack-allocated, persistent. The smoothing curves work
  correctly and Update() generates zero garbage.

❯ explain that "smoothing curves"                                               

⏺ Great question — "smoothing curve" is informal language for the mathematical 
  shape of the transition that SmoothDamp produces.

  ---
  Without smoothing — a step function

  If you wrote the azimuth directly with no smoothing:

  _azimuth = rawAzimuth;  // instant snap every frame

  The value teleports frame to frame. Plotted over time it looks like:

  value
    |      target──────────
    |
    |──────
    |
    +──────────────────── time

  In audio terms: pan jumps hard left → hard right in one frame. Sounds like a
  glitch.

  ---
  With SmoothDamp — a critically damped spring

  SmoothDamp models a spring with damping. The value accelerates toward the
  target, then decelerates as it approaches. Plotted:

  value
    |                  target ──────────
    |              __--
    |          _--
    |       _-'
    |    _-'
    |__-'
    +──────────────────── time
       ↑
       target changes here

  - Starts slow (low velocity)
  - Accelerates through the middle
  - Decelerates as it nears target
  - Never overshoots (critically damped — unlike a real spring)

  The shape of that S-curve is what people call the "smoothing curve". It's not
  a straight line (linear interpolation) and it's not a sudden jump — it's a
  physically natural motion.

  ---
  The smoothTime parameter controls the curve's width

  Mathf.SmoothDamp(_azimuth, rawAzimuth, ref _azimuthVel, 0.20f);
  //                                                       ↑
  //                                              reach target in ~0.2s

  A short smooth time = narrow curve = snappy response:

  value
    |         target ──────────────
    |       _-'
    |___--''
    +──────────────────── time

  A long smooth time = wide curve = sluggish, gradual response:

  value
    |                          target ──────
    |                      __--
    |                  _--
    |              _--
    |          _--
    |______--''
    +──────────────────── time

  ---
  Why each axis has a different smooth time

  From the doc:

  ┌───────────┬──────────┬──────────────────────────────────────────────────┐
  │   Axis    │ Smooth   │                       Why                        │
  │           │   time   │                                                  │
  ├───────────┼──────────┼──────────────────────────────────────────────────┤
  │ Azimuth   │ 0.20 s   │ Pan should feel responsive — you turned, it      │
  │           │          │ should follow quickly                            │
  ├───────────┼──────────┼──────────────────────────────────────────────────┤
  │ Alignment │ 0.35 s   │ Attention should lag slightly — filter flutter   │
  │           │          │ on micro-movements would sound nervous           │
  ├───────────┼──────────┼──────────────────────────────────────────────────┤
  │ Tilt      │ 0.30 s   │ Layer balance should feel gradual — arm          │
  │           │          │ movements are slow                               │
  ├───────────┼──────────┼──────────────────────────────────────────────────┤
  │ Distance  │ 0.50 s   │ You walk slowly — a fast distance response would │
  │           │          │  feel jittery                                    │
  └───────────┴──────────┴──────────────────────────────────────────────────┘

  Each axis has a different "feel" requirement, so each gets its own curve width
   — and therefore its own velocity field to preserve that curve's state across
  frames.

⏺ TrackMixer — turning movement into sound

  Every frame, after PoseAnalyzer has computed and smoothed the four axes,
  TrackMixer.Update() runs and applies four mappings to all four tracks.

  ---
  The lifecycle gate

  private bool _started;

  Update() does nothing until _started = true. This flag is set by
  StartScheduled(). So the modulation pipeline is completely inactive until
  audio actually begins playing. No wasted computation, no values being written
  to silent AudioSources.

  ---
  Mapping 1 — Attention → LPF cutoff

  This is the most complex mapping. Three sub-steps:

  Sub-step A — Attention (from PoseAnalyzer)

  Attention is already a clean [0, 1] value — not raw Alignment. It comes from:

  float t = Mathf.InverseLerp(attentionLow, attentionHigh, alignment);

  InverseLerp answers: "where does this value sit between two bounds?"

  alignment = 0.2  →  attention = 0.0  (not facing tree at all)
  alignment = 0.5  →  attention = ~0.48
  alignment = 0.85 →  attention = 1.0  (aimed directly at tree)

  It maps the raw dot product to a clean 0–1 range before any further math.
  Values outside the bounds are clamped to 0 or 1.

  Sub-step B — Logarithmic Hz interpolation

  float cutoffHz = cutoffMinHz * Mathf.Pow(cutoffMaxHz / cutoffMinHz,
  attention);

  Why logarithmic and not linear? Because human hearing is logarithmic — we
  perceive pitch in ratios, not absolute Hz differences.

  Linear interpolation at attention = 0.5:
  (800 + 20000) / 2 = 10400 Hz  ← sounds almost fully open, not halfway

  Logarithmic at attention = 0.5:
  800 × (20000/800)^0.5 = 800 × 25^0.5 = 800 × 5 = 4000 Hz  ← perceptually
  halfway

  Plotted — linear vs log:

  Hz
  20000 |              __-------  linear
        |         __--
        |    __--      ___-----   log
   4000 |___----------
    800 |
        +──────────────────── attention
        0                    1

  The log curve spends more "time" in the lower frequencies where the ear is
  most sensitive. It sounds smooth. The linear curve rushes to brightness too
  fast then barely moves in the upper range.

  Sub-step C — Distance ceiling

  After computing the attention-based cutoff, it gets capped:

  float ceiling = distanceCutoffCeiling.Evaluate(distance);
  cutoffHz = Mathf.Min(cutoffHz, ceiling);

  AnimationCurve.Evaluate(distance) reads a hand-authored curve at the current
  distance value and returns a Hz ceiling. At 8m, no matter how directly you
  face the tree, the filter can never open above ~3000 Hz. The mix stays dark
  and distant.

  This is an artistic override on top of the physics-based attention mapping.

  ---
  Mapping 2 — Azimuth → stereo pan

  float azimuthRad = azimuth * Mathf.Deg2Rad;
  float panBase = Mathf.Sin(azimuthRad);
  ch.SetPan(panBase * ch.PanWidth);

  Why Sin instead of just dividing the degrees by 180?

  Because the pan response should feel natural as you rotate around the tree,
  not mechanical. Sin gives you:

  azimuth   sin      perception
     0°      0.0     tree dead ahead — centred pan ✓
    30°      0.5     tree slightly right — moderate pan ✓
    90°      1.0     tree hard right — full pan ✓
   150°      0.5     tree behind-right — moderate (receding) ✓
   180°      0.0     tree directly behind — centred again ✓

  It saturates naturally toward ±90° and returns to centre as the tree passes
  behind you. A raw linear mapping would hit full pan at 90° and stay there for
  the entire rear half — unnatural.

  Each track scales panBase by its own PanWidth — so root_rave sweeps the full
  stereo field while soil stays more anchored.

  ---
  Mapping 3 — Tilt → per-track vertical layer balance

  float tiltGainDb = tiltGainRangeDb * (ch.TiltBias * tilt);

  TiltBias encodes which vertical layer each track "belongs to". tilt is the
  camera's Y forward component — positive when pointing up.

  At tilt = +0.8 (phone pointing up at canopy), TiltBias = +1.0 (canopy track):
  tiltGainDb = 6 × (1.0 × 0.8) = +4.8 dB  ← canopy boosted

  Same tilt, root_rave (TiltBias = -1.0):
  tiltGainDb = 6 × (-1.0 × 0.8) = -4.8 dB  ← root_rave cut

  The multiplication TiltBias × tilt is the entire mechanism. Two signed values
  multiplied — the sign determines whether this track gets louder or quieter for
   a given tilt direction.

  ---
  Mapping 4 — Distance → master gain offset

  float distGainDb = distanceGainDb.Evaluate(distance);

  Another AnimationCurve, this one mapping distance to a dB offset applied
  equally to all tracks. The curve is hand-authored — not a physics formula — so
   the composer/researcher can tune exactly how fast the mix recedes.

  ---
  Final gain computation — combining all three gain sources

  float totalDb = ch.BaseGainDb + tiltGainDb + distGainDb;
  totalDb = Mathf.Clamp(totalDb, gainMinDb, gainMaxDb);
  float linearGain = Mathf.Pow(10f, totalDb / 20f) * _muteGain;
  ch.Source.volume = linearGain;

  Four things happen here in sequence:

  1. Sum in dB space — the three gain contributions are added as dB values. This
   is correct: dB is a logarithmic scale, so adding dB values is equivalent to
  multiplying linear gains.

  2. Clamp to [-24, 0] dB — prevents the combination of boosts from clipping or
  the combination of cuts from making something inaudibly quiet.

  3. Convert dB → linear — 10^(dB/20) is the standard formula. Unity's
  AudioSource.volume is a linear [0, 1] value, not dB. You cannot write dB
  directly to it.

  4. Multiply by _muteGain — the tracking-loss ramp. Normally 1.0. If AR
  tracking is lost for 3+ seconds, this smoothly ramps to 0, fading all tracks
  to silence regardless of what the other calculations produce.

  ---
  The static branch (drone)

  Before running any of the above, TrackMixer checks:

  if (ch.IsStatic)
  {
      ch.SetCutoffHz(cutoffMaxHz);   // always fully open
      ch.SetPan(0f);                 // always centred
      ch.Source.volume = Mathf.Pow(10f, staticDb / 20f) * _muteGain;
      continue;                      // skip all four mappings
  }

  The drone never moves spatially. It holds the centre while the three active
  tracks sweep around it — that contrast is what makes the spatial movement
  perceptible to the listener.

  ---
  Summary of the full per-frame flow

  PoseAnalyzer.Update()
    → compute raw axes from AR camera + _treeBase
    → SmoothDamp each axis (preserving velocity fields)
    → compute Attention from Alignment

  TrackMixer.Update()
    → read 4 smoothed axes from PoseAnalyzer
    → for each TrackChannel:
        if static → fixed cutoff, fixed pan, fixed volume
        else:
            cutoffHz  = log interp(attention) capped by distance curve  →
  SetCutoffHz()
            pan       = Sin(azimuth) × PanWidth                         →
  SetPan()
            totalDb   = BaseGainDb + tiltGainDb + distGainDb → clamp → dB→linear
   × muteGain → volume

  Zero allocations. All config values from AudioSettingsConfig. Runs every
  frame.

❯ how the velocity fields are involved in the equations?                        

⏺ Great question — they're not in the equation you write. They're used inside
  SmoothDamp itself. Let me break it down.

  ---
  What you write

  _azimuth = Mathf.SmoothDamp(_azimuth, rawAzimuth, ref _azimuthVel, 0.20f);

  Four arguments:

  ┌─────────────────┬───────────────────────────────────────────┐
  │    Argument     │                What it is                 │
  ├─────────────────┼───────────────────────────────────────────┤
  │ _azimuth        │ current value (where we are now)          │
  ├─────────────────┼───────────────────────────────────────────┤
  │ rawAzimuth      │ target value (where we want to go)        │
  ├─────────────────┼───────────────────────────────────────────┤
  │ ref _azimuthVel │ velocity — read AND written by SmoothDamp │
  ├─────────────────┼───────────────────────────────────────────┤
  │ 0.20f           │ smooth time — how quickly to get there    │
  └─────────────────┴───────────────────────────────────────────┘

  ---
  What SmoothDamp does internally

  Under the hood, Unity solves a damped spring differential equation every
  frame. Roughly:

  acceleration = (target - current) × springForce - velocity × damping
  velocity     = velocity + acceleration × deltaTime
  current      = current + velocity × deltaTime

  Each frame:
  1. Reads _azimuthVel to know how fast the value is currently moving
  2. Computes how much to accelerate or decelerate toward target
  3. Updates the velocity
  4. Moves the current value by that velocity
  5. Writes the new velocity back into _azimuthVel via the ref

  ---
  Why ref matters

  ref means the variable is passed by reference — SmoothDamp can write back into
   it. Without ref, C# would pass a copy, SmoothDamp's velocity update would be
  lost, and the field would always read 0 next frame.

  // ref = SmoothDamp can modify _azimuthVel directly in memory
  Mathf.SmoothDamp(_azimuth, rawAzimuth, ref _azimuthVel, 0.20f);
  //                                     ↑
  //                         after this call, _azimuthVel holds the new velocity

  ---
  Traced across three frames

  Say the user suddenly rotates — azimuth jumps from 0° to 90°:

  Frame 1:
    _azimuthVel = 0.0   (no prior motion)
    SmoothDamp reads: current=0, target=90, vel=0
    → small acceleration, small movement
    → writes back: _azimuthVel = 180.0  (gaining speed)
    → _azimuth = 3.6°

  Frame 2:
    _azimuthVel = 180.0  (remembered from last frame)
    SmoothDamp reads: current=3.6, target=90, vel=180
    → still far from target, continues accelerating
    → writes back: _azimuthVel = 290.0
    → _azimuth = 21°

  Frame 3:
    _azimuthVel = 290.0
    SmoothDamp reads: current=21, target=90, vel=290
    → getting closer, starts to decelerate
    → writes back: _azimuthVel = 240.0
    → _azimuth = 45°

  ... continues until _azimuth ≈ 90, _azimuthVel ≈ 0

  The velocity field is the memory that connects each frame to the previous one.
   Remove it and every frame starts from zero velocity — you get the
  snap-to-target behaviour.

  ---
  Why a local variable breaks it

  void Update()
  {
      float vel = 0f;  // reset to zero every frame
      _azimuth = Mathf.SmoothDamp(_azimuth, rawAzimuth, ref vel, 0.20f);
      // vel is now e.g. 180.0 ... but it dies here, end of frame
  }

  Next frame vel is born again at 0. SmoothDamp always sees "no prior motion"
  and always produces a tiny first-step movement — effectively snapping to
  target over 1–2 frames with no smooth curve.

  ---
  One sentence summary

  The velocity field is the momentum the spring carries between frames —
  SmoothDamp reads it, updates it, and writes it back each frame via ref, and
  that continuity is what produces the smooth curve.

⏺ Good question. Let me trace the exact lifecycle.

  ---
  C# default initialization

  When Unity instantiates the PoseAnalyzer component (when the scene loads), C#
  automatically initializes every field that has no explicit value:

  private float _azimuthVel;    // C# sets this to 0f automatically
  private float _alignmentVel;  // 0f
  private float _tiltVel;       // 0f
  private float _distanceVel;   // 0f

  You don't write = 0f — it's guaranteed by the C# language spec. Every numeric
  field starts at zero. This is not Unity-specific, it's just C#.

  ---
  Full lifecycle from app launch

  Scene loads
      │
      ▼
  PoseAnalyzer component instantiated
      │
      ├── all float fields = 0f  (C# default)
      │   _azimuth    = 0f
      │   _azimuthVel = 0f       ← velocity starts here
      │   _alignment  = 0f
      │   _alignmentVel = 0f
      │   ... etc
      │
      ▼
  Awake() runs
      │
      ├── caches AR camera reference
      └── _treeBase = null  (tree not placed yet)
      │
      ▼
  Update() runs — frame 1
      │
      ├── rawAzimuth = 0  (no tree, returns 0)
      │
      ├── SmoothDamp(current=0, target=0, ref vel=0, 0.20f)
      │       → nothing to move toward, output = 0
      │       → vel written back = 0
      │
      └── _azimuth stays 0, _azimuthVel stays 0
      │
      ▼
  Update() runs — frame 2, 3, 4...  (same, tree still not placed)
      │
      ▼
  User places tree  ←─── first interesting moment
      │
      ├── SetTreeBase(transform) is called
      └── _treeBase is now set
      │
      ▼
  Update() runs — next frame
      │
      ├── rawAzimuth = e.g. 45°  (camera is 45° off from tree)
      │
      ├── SmoothDamp(current=0, target=45, ref vel=0, 0.20f)
      │       → vel was 0, starts accelerating
      │       → writes back: vel = ~90
      │       → _azimuth moves to ~1.8°
      │
      ▼
  Update() — frame after
      │
      ├── SmoothDamp(current=1.8, target=45, ref vel=90, 0.20f)
      │       → continues the curve...

  ---
  The key insight

  The velocity starts at 0f by default, which is correct — the value genuinely
  isn't moving at app launch. The spring starts from rest and that's the right
  physical starting condition.

  The only moment it would be wrong is if you wanted the value to start already 
  in motion — which this app never needs. The tree isn't placed yet, nothing is
  moving, zero velocity is accurate.

❯ is .normalized a built int function for Vec3 in c#?                           

⏺ Yes — .normalized is a built-in property on Unity's Vector3 struct. It's not
  part of standard C#, it's provided by Unity.

  ---
  What it does

  It returns a new vector pointing in the same direction but with a length
  (magnitude) of exactly 1.0. The original vector is not modified.

  Vector3 v = new Vector3(3f, 0f, 4f);  // length = 5
  Vector3 n = v.normalized;             // length = 1, same direction
  // n = (0.6, 0, 0.8)

  The math:

  normalized = vector / vector.magnitude
             = (x, y, z) / √(x² + y² + z²)

  ---
  Why it's used in the azimuth calculation

  Vector3.SignedAngle(camFwdXZ.normalized, toTreeXZ.normalized, Vector3.up);

  SignedAngle only cares about direction, not length. But if you pass vectors of
   different lengths, floating point arithmetic can introduce tiny errors into
  the angle result.

  Normalizing both vectors first guarantees both have length 1 — the angle
  calculation is then purely about direction, with no length influence.

  ---
  .normalized vs Vector3.Normalize()

  Unity gives you two ways:

  v.normalized        // returns a NEW normalized vector, v is unchanged
  Vector3.Normalize(v) // same, static form
  v.Normalize()       // modifies v IN PLACE, returns void

  In PoseAnalyzer the property form is used because you want a normalized copy
  for the angle calculation — you don't want to destroy the original vector,
  which is still needed for other things like .magnitude (distance).

⏺ Yes, that's a ternary operator — a compact if/else. Exactly equivalent to:

  if (toTreeXZ.sqrMagnitude > 0.0001f)
      azimuth = Vector3.SignedAngle(camFwdXZ.normalized, toTreeXZ.normalized,
  Vector3.up);
  else
      azimuth = 0f;

  ---
  The syntax broken down

  azimuth = condition ? valueIfTrue : valueIfFalse;

  ┌────────┬─────────────────────────────────────────────────┐
  │ Symbol │                     Meaning                     │
  ├────────┼─────────────────────────────────────────────────┤
  │ ?      │ "if condition is true, use what comes after me" │
  ├────────┼─────────────────────────────────────────────────┤
  │ :      │ "otherwise use what comes after me"             │
  └────────┴─────────────────────────────────────────────────┘

  Read it aloud as: "assign azimuth — if sqrMagnitude > 0.0001 then SignedAngle,
   else 0"

  ---
  Why the guard condition exists

  toTreeXZ.sqrMagnitude > 0.0001f is checking: is the tree far enough away to 
  have a meaningful direction?

  If the user is standing almost exactly on top of the tree base, toTreeXZ
  becomes a near-zero vector. Passing a near-zero vector to SignedAngle produces
   garbage — the direction is undefined when there's no distance. Unity may
  return NaN or a random angle.

  The threshold 0.0001f is a small epsilon — essentially "is this vector
  non-zero?" If yes, compute the angle safely. If no, just return 0f.

  ---
  Why sqrMagnitude and not magnitude?

  // magnitude — involves a square root (slow)
  toTreeXZ.magnitude > 0.01f

  // sqrMagnitude — no square root (fast)
  toTreeXZ.sqrMagnitude > 0.0001f

  magnitude requires √(x² + y² + z²) — a square root every frame. sqrMagnitude
  skips the root and just returns x² + y² + z². Since this runs in Update()
  every frame, avoiding the square root is a small but deliberate optimization.
  The threshold is squared accordingly (0.01² = 0.0001).

⏺ ComputeAttention — line by line

  ---
  The method signature

  private float ComputeAttention(float align)

  - private — only callable from inside PoseAnalyzer
  - float — returns a single decimal number
  - align — receives the raw Alignment value (the dot product, range roughly -1
  to 1)

  ---
  Line 1 — the null guard

  if (_config == null) return 1f;

  If AudioSettingsConfig was never wired in the Inspector, _config is null.
  There are no threshold values to use. Rather than crashing or returning 0f
  (which would lock the LPF at 800 Hz — muffled silence), it fails open —
  returns 1f meaning "fully open filter, full brightness."

  Audio is always audible. The app never silently breaks because of a missing
  Inspector reference.

  The return here exits the method immediately — everything below is skipped.

  ---
  Line 2 — InverseLerp

  float t = Mathf.InverseLerp(_config.attentionLow, _config.attentionHigh,
  align);

  InverseLerp answers: "where does align sit between these two bounds, expressed
   as 0 to 1?"

  InverseLerp(low, high, value)

  value ≤ low   → 0.0
  value = mid   → 0.5
  value ≥ high  → 1.0

  With the default config values (attentionLow = 0.2, attentionHigh = 0.85):

  align = 0.0  → t = 0.0   (not facing tree at all)
  align = 0.2  → t = 0.0   (just at the threshold)
  align = 0.5  → t = 0.48  (roughly halfway)
  align = 0.85 → t = 1.0   (aimed directly at tree)
  align = 1.0  → t > 1.0   (beyond the high bound — not clamped yet)

  This is why attentionLow and attentionHigh exist as config values — they
  define the dead zone (below 0.2 nothing happens) and the saturation point
  (above 0.85 fully open).

  ---
  Line 3 — Clamp01

  return Mathf.Clamp01(t);

  Clamp01 constrains the value to exactly [0, 1]. It handles the edge case from
  above where align > attentionHigh would produce t > 1.0. Without it, the LPF
  formula could receive values above 1 and produce cutoff frequencies above
  20000 Hz — meaningless and potentially unpredictable.

  t = -0.3  → 0.0
  t =  0.7  → 0.7   (unchanged)
  t =  1.4  → 1.0

  ---
  The full flow visualized

  align (raw dot product)
    │
    ▼
  InverseLerp — maps [attentionLow → attentionHigh] to [0 → 1]
    │
    ▼
  Clamp01 — enforces hard [0, 1] bounds
    │
    ▼
  Attention — clean [0, 1] ready for log LPF formula

  ---
  Why not pass align directly to the LPF formula?

  Because align is a dot product — its range depends on geometry, it has no
  clean bounds, and values below 0.2 should all mean "no attention." InverseLerp
   + Clamp01 converts a messy geometric value into a clean, bounded, musically
  meaningful control signal.
